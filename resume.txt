проект - Python-приложение, которое одновременно взаимодействует с двумя внешними сервисами: Telegram и Jira.
Чтобы всё это работало, в проекте используются aiogram, FastAPI, Uvicorn, ngrok и механизм OAuth 2.0.

когда запускается main.py создаётся объект Bot, которому передаётся токен Telegram-бота из файла конфигурации
После создаётся Dispatcher (управляет обработкой входящих сообщений и событий), к нему подключается router из handlers.py
В handlers.py: обработчики команд и нажатий на кнопки
Dispatcher получает событие и определяет, какой обработчик его обработает для этого используют Router
(объединяет обработчики), а сами обработчики выполняют нужные действия.

чтобы каждый пользователь мог подключить собственный Jira-аккаунт реализован механизм OAuth 2.0
в ответ на команду /connect, бот формирует ссылку на стр-у авторизации Atlassian и Пользователь разрешает приложению доступ к данным.
После подтверждения Atlassian перенаправляет пользователя обратно в приложение (адрес указан в настройках OAuth-приложения)
Этот процесс называется OAuth callback. В URL callback Atlassian передает параметр code, ктр приложение обменивает на токены доступа.
+ передаётся state (используется для проверки того, что ответ относится к начатому процессу авторизации)

Чтобы принять этот callback, в проекте используется отдельное веб-приложение, написанное с помощью FastAPI в файле oauth_server.py
FastAPI позволяет описывать HTTP-маршруты, те адреса, по которым приложение принимает запросы.
(пример маршрута: обработка возвращения пользователя после авторизации в Atlassian)
Чтобы FastAPI-приложение было доступно для получения запросов: его необходимо запустить (тут с помощью Uvicorn)
Затем OAuth-сервер запускается как отдельная асинхронная задача - позволяет ему работать одновременно с ботом, не мешая обработке сообщений.

тк тут OAuth-сервер работает локально у меня на компе, Atlassian не может напрямую обратиться к localhost
Поэтому используется ngrok - создаёт публичный HTTPS-адрес и перенаправляет поступающие на него запросы на
локальный порт 8000, где работает Uvicorn.
Поэтому, когда Atlassian выполняет перенаправление после авторизации, запрос сначала приходит на публичный адрес ngrok,
затем ngrok передаёт его Uvicorn, а Uvicorn направляет его в нужный маршрут FastAPI-приложения.
Так, ngrok обеспечивает доступ к локальному OAuth-серверу извне, Uvicorn принимает HTTP-запросы, а FastAPI обрабатывает их.

После получения callback приложение использует временный authorization code (от Atlassian) и отправляет запрос к
Atlassian API, чтобы обменять его на access token и refresh token.
Access token — токен, с помощью которого бот выполняет запросы (показать задачи и тд) к Jira API от имени конкретного пользователя.
У access token ограниченный срок действия, он не может использоваться бесконечно. Для получения нового токена применяется
refresh token. Когда access token истекает, приложение использует refresh token, чтобы запросить у Atlassian новую пару токенов.
Это позволяет пользв продолжать работать с Jira без необходимости каждый раз проходить авторизацию заново

Полученные токены и информацию о подключённом Jira-аккаунте приложение сохраняет в базе данных users.db.
Благодаря этому бот различает пользователей и понимает, какой Jira-аккаунт использовать при обработке очередной команды.
Отдельно в проекте используется база notifications.db, в которой хранится инфа об истории уведомлений о дедлайнах.

В main.py также запускается планировщик APScheduler. Он отвечает за автоматическую проверку дедлайнов.
В него добавляется функция check_deadlines, которая должна выполняться каждые 15 минут.

Все эти компоненты работают в рамках одного приложения благодаря асинхронному механизму Python — asyncio.

подробнее про токены:
--------------------------------------------------------------------------------
когда пользователь отправялет /my_tasks бот должен получить список задач пользователя из Jira
Для этого приложение формирует HTTP-запрос к Jira API и передаёт в нём access token. Упрощенно выглядит так:
    GET https://api.atlassian.com/ex/jira/CLOUD_ID/rest/api/3/search/jql
    Authorization: Bearer ACCESS_TOKEN
Atlassian получает запрос, проверяет токен и его разрешения. Если всё в порядке, возвращает данные о задачах.
Так, access token позволяет приложению обращаться к Jira API от имени пользователя, в пределах выданных разрешений
! но access token действует ограниченное время. Когда он истекает, использовать его для новых запросов уже нельзя.

А Refresh token — токен обновления. Нужен, чтобы получать новые access token без повторного прохождения авторизации пользователем

Обмен authorization code на токены:
Когда браузер перенаправляется на callback URL, в адресе передаются code и state.
Потому что браузер пользователя не должен напрямую получать и передавать приложению долгосрочные секреты доступа.
Сначала браузер получает временный одноразовый код, а затем уже сервер обменивает его на токены напрямую через
защищённый запрос к Atlassian.

за что отвечает каждый файл:

Представим, что пользователь уже подключил Jira и отправляет /my_tasks.
Сначала Tg передаёт сообщение приложению. Aiogram принимает его, Dispatcher определяет нужный обработчик через
подключённый Router, и запускается функция из handlers.py.

Обработчик получает Telegram ID пользователя и проверяет, подключён ли его Jira-аккаунт. Затем получает выбранный проект
 из user_store.py и вызывает get_my_tasks() из jira_client.py.

jira_client.py обращается к user_store.py, чтобы найти запись пользователя в users.db. Токены расшифровываются,
проверяется срок действия access token. Если он скоро истечёт, приложение использует refresh token, получает новую пару
 токенов и сохраняет её обратно в базу.

После этого jira_request() формирует HTTP-запрос к Jira API, добавляет access token в заголовок Authorization и
отправляет запрос. Jira проверяет токен и разрешения пользователя, выполняет запрос и возвращает список задач.

jira_client.py обрабатывает полученные данные и передаёт их обратно в handlers.py. Обработчик формирует понятное
 сообщение и отправляет его пользователю через aiogram.

Как именно oauth_server.py принимает callback?
oauth_server - задача принять HTTP-запрос, извлечь параметры и передать их дальше в сервис авторизации
создаётся FastAPI-приложение. Его объект называется app. Именно его импортирую в main.py и передаю Uvicorn
    @app.get("/oauth/callback", response_class=HTMLResponse)
Это объявление HTTP-маршрута. Оно означает: если на сервер придёт GET-запрос по адресу /oauth/callback,
FastAPI должен вызвать функцию, которая расположена ниже (адрес ATLASSIAN_REDIRECT_URI)

в функции oauth_callback из URL получаем параметры code, state, error. Это делается с помощью FastAPI, сама строку не разбираю
также настроена обработка ошибок
+ FastAPI передаёт полученные параметры в функцию complete_oauth() из auth_service.py
Если авторизация прошла успешно - FastAPI возвращает браузеру HTML-страницу с подтверждением подключения.


auth_service.py
отвечает за формирование ссылки, проверку состояния авторизации, обмен кода на токены, получение доступных Jira-сайтов
и сохранение подключения
Формирование ссылки авторизации с помощью CLIENT_ID, CLIENT_SECRET, REDIRECT_URI
в массиве SCOPES задаются разрешения, которые приложение запрашивает у пользователя (те scopes ктр указывала в настройках Atlassian OAuth)
разрешения такие: на чтение данных jira (задач и тд), на изменение данных, чтение инфы о пользователях, на обновление токенов

в create_authorization_url формируется ссылка, по которой пользователь будет переходить для подключения Jira
с помощью state в ссылках идентифицируются разные пользователи
+ создается словарь с параметрами которые будут переданы Atlassian в url авторизации ()

в функции exchange_code - Обмен authorization code на токены
приложение отправляет POST-запрос на сервер авторизации Atlassian. в запросе передаются (grant_type="authorization_code"
client_id, client_secret, code, redirect_uri). Atlassian проверяет запрос и, если всё правильно, возвращает JSON-ответ с токенами

в get_accessible_resources - Получение доступных Jira-сайтов
выполняется GET-запрос к Atlassian API, В заголовке Authorization передаётся access token.

в complete_oauth объединяются все предыдущие действия


jira_client.py
отвечает за взаимодействие с Jira API. Тут функции получения проектов, задач, создания задач и изменения статусов
почти все эти функции используют одну общую функцию jira_request. Она выполняет запросы к Jira от имени конкретного пользователя

как регистрировалось приложение в atlassian

Client ID — идентификатор твоего приложения. чтобы Atlassian понял что это именно мое приложение
Client Secret — секрет приложения. нужен серверной части проекта, чтобы подтвердить Atlassian, что запрос на обмен authorization code отправляет зарегистрированное приложение
Redirect URI — адрес, куда Atlassian возвращает пользователя после авторизации (те адрес ngrok) Он совпадает с адресом в настройках OAuth-приложения, и с адресом в запросе авторизации и обмена кода на токены

+ SCOPES указывала в настройках приложения, в auth_service.py они такие же
